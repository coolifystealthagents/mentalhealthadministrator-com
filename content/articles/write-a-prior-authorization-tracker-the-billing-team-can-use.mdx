## How to approach: Write a prior authorization tracker the billing team can use

A prior authorization tracker should show which requests are pending, approved, denied, or expiring. Start with the client, the payer, the service, and the request date. A tracker that only lists the request number does not support a follow-up. If the source is unclear, route the question instead of guessing.

Keep the tracker current. A request that is approved but not recorded will cause a denied claim. The team should update the tracker when the decision arrives. If the source is unclear, route the question instead of guessing.

## Record the request and the payer

Record the client, the payer, the service, and the date the request was submitted. Include the reference number and the person who submitted it. A request without a reference is hard to trace. Keep the evidence with the record rather than in a separate log.

Record the expected decision time and the follow-up date. A payer that is slow should be called, not waited on. The tracker should show the next action. If the source is unclear, route the question instead of guessing.

## Record the decision and the expiry

Record whether the request was approved, denied, or partially approved. Include the approved units and the expiry date. A denial should record the reason and the appeal deadline. If the source is unclear, route the question instead of guessing.

Set a reminder before the expiry. An authorization that expires without a renewal may cause a denied claim. The reminder should be visible to the billing team. Separate what was observed from what was assumed.

## Record the next action

Every open row needs an owner and a date. The action might be a follow-up call, an appeal, a clinical note, or a client conversation. A row without an action will sit. Test the rule on one real call before applying it to the queue.

Close the row only when the service is authorized or the denial is resolved. A closed row without evidence is not a closure. Name the owner in the same line as the action. A control that depends on memory is not yet a control.

## Review the tracker monthly

Look for payers with long decision times or frequent denials. A pattern may point to a documentation or coding problem. Share the pattern with the billing and clinical teams. Keep the evidence with the record rather than in a separate log.

Update the tracker after a payer change. A new portal or rule may require a new field. The goal is a clean claim, not a longer spreadsheet. Keep the boundary visible in the place where the work is assigned.
