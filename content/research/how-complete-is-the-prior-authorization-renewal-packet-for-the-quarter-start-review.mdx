## Question and scope

This review asks a narrow question: when a behavioral health practice prepares a prior-authorization renewal packet, how often does the packet contain the administrative fields that a payer review needs before the next scheduled visit? The question is about completeness, not about whether the payer will approve the request. A complete packet can still be denied, and an incomplete packet can sometimes be approved after follow-up. Keeping those outcomes separate prevents the review from turning a documentation measure into a guess about clinical merit.

The scope should be written before any packet is read. Decide which payers, service lines, clinicians, and date range belong in the review. Decide whether the practice will count packets prepared for new authorizations or only renewals. Include the units of the thing being measured, such as one packet per authorization per renewal cycle. Without that boundary, the denominator drifts toward whichever files are easiest to find.

A quarter-start window is useful because renewal volume often changes with new intakes and benefit resets. The review should state the exact start and end dates and the date on which each packet's completeness was judged. Completeness is a snapshot, not a permanent property. A packet that was incomplete on the observation date may be complete today, and the finding should say so.

## Population and unit of analysis

The population is every renewal packet prepared for a scheduled visit inside the observation window. The unit is one packet tied to one authorization and one visit date. If a single client has two authorizations for two services, count two packets. If a renewal is reopened after a denial, decide whether it is the same unit or a new cycle, and apply that rule to every file. Record the rule in the collection log so a second reviewer can reproduce the count.

Exclude packets that were never submitted because the visit was cancelled before preparation began. Include packets that were submitted late, because lateness is part of the process being reviewed. Include packets that were prepared by a covering coordinator, because coverage is a normal condition in a small practice. Do not exclude a difficult file merely because it does not fit the usual workflow.

Stratify the sample by payer, service line, and preparer role if the practice has enough volume. A small practice may only be able to stratify by payer and month. The strata should be chosen before collection and reported with the result. A rate that hides a weak stratum can make the overall number look better than the experience of one team.

## Definitions and measures

Define completeness as the presence of a fixed list of administrative fields on the observation date. A practical list includes the client identifier, the authorization number if one exists, the covered service, the requested dates, the treating clinician, the payer reference, and the date the packet was submitted or is due. Add a field for the source document used to confirm each value. Keep the list short enough that a reviewer can apply it consistently.

Treat missing, unavailable, and confirmed negative values as different results. A field that the practice is not permitted to collect is not the same as a field the coordinator forgot. A field that the payer has not yet assigned is not the same as a blank. The review should report each category separately, because the fixes are different. Combining them into one missing rate hides the actionable part.

The primary measure is the share of packets missing at least one required field. A secondary measure is the count of missing fields per packet. Report both, because a practice with one missing field in many packets has a different problem from a practice with many missing fields in a few. Also report the oldest incomplete packet and the number of packets that reached the visit date without a recorded submission.

## Data sources and collection

Use the practice's own authorization tracker as the primary source and the payer portal as the confirmation source when access is available. Do not rely on memory or on a coordinator's verbal summary. If the tracker and the portal disagree, record both values and mark the discrepancy. The discrepancy itself is a finding about the tracker, even when the packet turns out to be complete.

Collect the data in one session where possible, using a fixed export from the tracker. Freeze the export so later edits do not change the observed values. Store the export with the review file and note the date and time it was created. If the export must be refreshed, keep the earlier version and label the new one. A moving source makes a completeness rate impossible to defend.

Use a pseudonymous key for each packet and keep the crosswalk in an approved system with restricted access. The review file should not contain clinical narrative or unnecessary identifiers. Record the reviewer's initials, the observation date, and any reason a field could not be checked. A second reviewer should be able to repeat the classification from the same source without asking the first reviewer what they meant.

## Evidence standard

A field counts as present only when the reviewer can point to a stored value with a date or source. A checked box without a supporting value is not enough. A value copied from a prior authorization is not automatically valid for the current cycle. The reviewer should be able to say where the value came from and when it was confirmed. That standard turns completeness from an impression into evidence.

When a packet is challenged, the defense is the field list, the observation date, and the source record. Keep those three elements together in the review file. Do not add a field to the list after collection without labeling the change and the date. A definition that changes mid-review can still be useful if the earlier classification is preserved and the new rule is applied only to later files.

The review should state what it does not measure. It does not measure clinical appropriateness, payer decision quality, or whether the service was ultimately delivered. It does not prove that a complete packet will be paid. Stating those limits protects the reader from overreading the result and keeps the finding focused on the administrative process the practice can actually change.

## Analysis and reporting

Report the primary rate with its numerator, denominator, and observation window. Report the field-level missing counts in a small table so the reader can see which field drives the result. Report the oldest incomplete packet and the number of packets that reached the visit date without a submission. Those tail measures often matter more than the average because a single late packet can disrupt a schedule.

Compare the result with the previous quarter only if the field list and the population rule are the same. If the method changed, label the comparison as descriptive and explain the change. A trend built on different definitions is not a trend. The practice administrator should be able to see whether the change is real or an artifact of the review design.

Write a short interpretation that names one or two process steps to examine. For example, a high missing rate on the payer reference may point to the intake handoff, while a high rate on the treating clinician may point to the scheduling template. Avoid recommending a new form until the review shows which field is actually missing. The report should end with a decision the practice can make, not a list of everything that could be improved.

## Limits and sources of error

The largest source of error is an unstable denominator. If packets are added or removed during collection, the rate can move without any change in practice behavior. Freeze the export and record the inclusion rule. A second source of error is reviewer drift, where one person interprets a field more strictly than another. A short calibration sample and a written field definition reduce that risk.

The tracker may be incomplete in ways the review cannot see. A packet prepared outside the tracker may be missing from the population entirely. Ask the scheduling and billing teams whether any renewal work happens in a separate system. If it does, either include it or state the coverage limit. A review that silently omits a workstream can produce a confident but wrong result.

The finding is a description of documentation at one point in time. It is not a verdict about the coordinator or the clinician. A missing field may reflect an unclear form, a payer delay, or a handoff that was never designed. Report the result without attributing motive, and use the pattern to change one step. That stance makes the next review easier to run and easier to trust.

## Review cadence

Repeat the review at each quarter start using the same field list and population rule. Keep the previous review file so the comparison is possible. If the practice changes its tracker, record the change and treat the first review after the change as a new baseline. A cadence that survives a tool change is more useful than a perfect method that is abandoned.

Assign one owner for the review and one backup. The owner should be able to export the data, apply the definitions, and write the short report. The backup should run the review at least once so the method is not trapped in one person's memory. A review that depends on a single coordinator is itself a continuity risk.

Close the cadence with a dated follow-up on the one process change the review selected. At the next quarter start, check whether that change moved the field it was meant to move. If it did not, examine the implementation before changing the definition. The purpose of the cadence is to learn from a small number of controlled changes, not to produce a new report every quarter.
